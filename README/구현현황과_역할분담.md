## 현재 상태 한눈에 보기

| 영역 | 상태 | 현재 모습 | 다음 핵심 작업 |
| --- | --- | --- | --- |
| 공통 계약·타입 | 구현됨 | `CsCase`, 상태, 결정값, Tool 계약이 ver4.3과 일치 | 계약 변경 시 A·B 사전 합의 |
| Mock Data·Policy·Risk | 부분 구현 | 사실 데이터, Policy 제약, Risk 차단 행동 제공. 날짜·시각은 `2026-09-30`에 고정 | 실행 시점과 무관한 Demo 시간 기준으로 수정하고 Agent 판단에 적용 |

| 가상 로그인·역할 권한 | 부분 구현 | 역할별 진입 화면만 존재하고 모든 역할 Route를 직접 열 수 있음 | 가상 계정 세션, Route 보호, 역할별 데이터 제한 |
| Customer 화면 | 부분 구현 | 고객 문장으로 Case 생성, 추가 대화와 첨부 이름 저장 | 주문 선택, 진행 상태, 결과·이력, Agent Loop 연결 |
| Merchant 화면 | 부분 구현 | Queue, 선택형 응답, 대화·이력은 구현. 한 화면에서 세 매장 전환 가능 | 실제 Agent 요청, 로그인 계정의 매장 제한, 샘플 UI 제거 |
| Human CS 화면 | 부분 구현 | Queue, 상세, 처리 결과 저장, 정책 화면, Summary 표시 | 전체 Risk Flag 표시, 실제 이관 연결 후 샘플 UI 제거 |
| Dynamic Agent Loop | 미구현 | 타입만 정의됨 | 다음 행동 선택, Tool 실행, 재판단, 종료 조건 구현 |
| 화면 간 전체 흐름 | 미완료 | 세 화면은 `main`에 합쳐져 있으나 샘플이 Queue를 생성 | 한 `caseId`로 Customer → Merchant/CS → Customer 검증 |

가장 큰 미완료 항목은 **Dynamic Agent Loop**다. 현재 Customer 문의는 Case에 저장되지만, 다음 Tool이나 Action을 고르지 않는다. 따라서 Merchant와 Human CS Queue는 임시 샘플 버튼으로 채운다.

## 문서 적용 우선순위

1. `COMMON_AGENT_CONTRACT ver4.3`: 데이터, 상태, Tool, Policy, Risk, Guardrail의 최종 기준
2. `배달 플랫폼 CS AI Agent PoC 기획서 틀`: 앞으로 구현할 기능 범위와 화면 요구사항
3. 현재 코드: 이 문서에서 구현 여부를 판정하는 근거

기획서가 Risk 발생이나 고객·매장 주장 충돌을 즉시 이관하도록 표현하더라도, 공통 계약의 해결 시도와 Action별 차단 원칙을 우선한다. 기획서의 `PACKED`, `unknown`, `CHECKING_ORDER`·`CHECKING_DELIVERY`도 공통 계약의 `CLAIMS_PACKED`, `other`, `CHECKING_DATA`로 맞춰 구현한다.

## 반드시 지킬 경계

### 1. Agent는 고정 Workflow가 아니다

문의 유형별 Tool 순서를 하드코딩하지 않는다. Agent는 현재 `CsCase`와 이전 Tool Observation을 보고 다음 행동을 선택한다.

```text
현재 Case와 Observation 확인
→ 다음 행동 선택
→ 필요한 Tool 호출
→ 결과를 toolHistory와 Case에 저장
→ 종료 조건 확인
→ 필요하면 다시 판단
```

Demo A~E는 테스트의 예상 결과이지 실행 순서가 아니다. `demoCaseId`나 문의 유형으로 전용 처리 경로를 만들지 않는다.

### 2. Tool과 Agent Loop의 책임을 분리한다

- Tool은 Mock 또는 외부 시스템의 결과만 `ToolResult<T>`로 반환한다.
- Tool은 Case, `history`, `toolHistory`를 직접 바꾸지 않는다.
- 상태 변경, Observation 저장, 다음 행동 선택은 Agent Loop가 담당한다.
- `refund`와 `redelivery`는 실제 처리 없이 Mock 결과만 반환한다.

현재 `requestMerchantConfirmation`과 `escalateToHuman`은 이 원칙대로 결과만 반환한다.

### 3. Merchant 응답은 확인 종료와 다르다

1. Agent가 확인 요청을 만들고 Case를 `WAITING_MERCHANT`로 저장한다.
2. Merchant의 선택은 `MerchantResponse`에 저장되지만 확인 상태는 `waiting`이다.
3. 선택 뒤 설명은 기존 응답을 자동으로 바꾸지 않는다.
4. 설명이 부족하거나 선택과 충돌하면 Agent가 후속 질문한다.
5. 충분한 정보가 모인 뒤에만 `completeMerchantConfirmation`을 호출한다.
6. `completed` 이후 같은 Case의 본 Agent Loop를 다시 실행한다.

`waiting` 응답만으로 환불, 재배달, Human CS 이관을 확정하면 안 된다.

### 4. Human CS 처리는 현재 계약에서 종결 처리다

`recordHumanCsResolution`은 다섯 가지 Human CS Action 중 하나를 저장하고 Case를 `CLOSED`로 바꾼다. `request_more_info`와 `request_additional_confirmation` 이후 고객 채팅을 다시 여는 흐름은 ver4.3 범위에 없다. 이 흐름을 추가하려면 구현 전에 공통 계약을 변경해야 한다.

### 5. Risk는 필요한 Action만 제한한다

- `duplicate_refund`: `mock_refund`만 제한
- `frequent_refund`: 검토 신호이며 Action을 자동 차단하지 않음
- `order_claim_mismatch`: `mock_refund`, `mock_redelivery` 제한
- `evidence_mismatch`: `mock_refund`, `mock_redelivery` 제한

Risk Flag가 있다는 이유만으로 즉시 Human CS로 이관하지 않는다.

## 남은 작업 상세

아래 작업 ID별 구현 범위와 완료 기준을 따른다.

### 담당자 A: Agent Loop

#### A-01 · Intent Classification과 Dynamic Agent Controller 구현

고객 자연어를 `delivery_delay`, `missing_item`, `wrong_delivery`, `other`로 분류한다. 이어서 `AgentController.decideNextAction(caseData)`와 `runNextStep(caseId)`를 구현해 현재 Case와 이전 Observation으로 다음 행동을 선택하고 종료할 때까지 반복한다. 문의 유형별 고정 Tool 순서와 Demo ID 전용 분기는 만들지 않는다.

#### A-02 · Tool 실행과 이력 기록 연결

Agent가 선택한 Tool만 호출한다. 모든 성공·실패 결과는 입력, 결과, step, 시작·종료 시각과 함께 `toolHistory`에 남긴다. 상태 변경과 업무 이벤트는 `history`에 남긴다.

#### A-03 · 고객 추가 질문과 증빙 요청

정보가 부족하면 `ASK_CUSTOMER`로 질문하고 필요하면 증빙을 요청한다. `COLLECTING_INFO` 또는 `WAITING_EVIDENCE`에서 고객 답변을 받은 뒤 새 Case를 만들지 않고 같은 Case를 재개한다.

#### A-04 · Merchant 확인 요청 연결

`requestMerchantConfirmation` 결과를 Case에 저장하고 상태를 `WAITING_MERCHANT`로 바꾼 뒤 본 Loop를 멈춘다. `MERCHANT_REQUESTED` 이력과 Tool 로그를 남기며 실제 Customer Case가 해당 매장의 Queue에 나타나야 한다.

#### A-05 · Merchant 확인 대화와 본 Loop 재개

선택 없이 들어온 자연어만 Agent가 `MerchantResponse`로 구조화한다. 선택 뒤 설명은 기존 응답을 자동 변경하지 않는다. 선택과 설명이 충돌하면 후속 질문으로 뜻을 확인하고, 질문 중에는 `WAITING_MERCHANT`와 `waiting`을 유지한다. 충분한 정보가 모이면 `completeMerchantConfirmation`을 호출하고 같은 Case의 본 Loop를 재개한다.

`waiting` 응답만으로 환불, 재배달, Human CS 이관을 확정하면 안 된다.

#### A-06 · Policy·Risk·Guardrail 적용

`allowedActions`, `constraints`, `blockedActions`를 함께 적용한다. 중복 보상, 주문 불일치 보상, 허용 범위 초과 보상, 충돌 상태 자동 보상을 막는다. Risk Flag만으로 즉시 이관하지 않고 허용된 추가 질문과 Tool 조회로 해결 가능한지 먼저 판단한다.

#### A-07 · 자동 처리 종료 저장

선택한 Action과 Mock 실행 결과를 `decision`, `finalAction`, `finalActionResult`에 저장하고 고객용 최종 문장과 완료 시각을 남긴다. 자동 처리 Case는 `AUTO_RESOLVED`가 되어야 하며 실제 환불·재배달로 오해하지 않도록 Mock 처리임을 표시한다.

#### A-08 · Human CS 이관 조건과 저장

고객의 명시적 사람 상담 요청, 최대 step 초과, 반복 Tool 실패, 허용된 해결 방법 소진 시 이관한다. `ESCALATED`, `escalationReason`, `agentSummary`와 전체 맥락을 저장해 실제 Customer Case가 Human CS Queue에 나타나게 한다.

#### A-09 · 이관 이후 Agent 중단

`ESCALATED` Case와 Human CS가 처리한 `CLOSED` Case는 본 Loop에서 제외한다. Human CS 처리 후 Agent가 상태나 최종 결과를 덮어쓰면 안 된다.

### 담당자 A: Customer 화면

#### A-10 · 주문 선택·자동 제안과 주문 카드 데이터 연결

문의 유형에 따라 주문을 고정하는 현재 매핑을 제거하고 로그인 고객의 최근 주문 목록에서 대상을 선택하게 한다. 가장 최근 주문을 기본으로 제안하되 고객이 바꿀 수 있어야 한다. 주문 카드도 공통 Mock Data를 읽고, 선택한 `customerId`, `orderId`, `storeId`로 Case를 생성한다.

#### A-11 · Case 상태와 고객 진행 상태 연결

공통 `CaseStatus`를 접수, 정보 확인 중, 사장님 확인 중, 자동 처리 완료, 상담원 검토 중, 처리 완료로 매핑한다. Case 구독으로 다른 화면의 변경을 새로고침 없이 반영한다. Customer UI의 `ready`, `working`, `waiting`, `resolved`를 공통 상태로 사용하지 않는다.

#### A-12 · 최종 결과와 이전 문의 표시

자동 처리와 `humanCsResolution`의 Action, 안내 문장, 처리 시각을 Customer 화면에 표시한다. 이전 문의는 `getCasesForRole('customer', customerId)`로 본인 Case만 조회한다.

#### A-13 · 카메라·첨부 미리보기와 고객 알림

모바일 웹에서 카메라를 바로 호출하고 촬영한 사진을 문의에 첨부할 수 있게 한다. 이미지 미리보기를 제공하고 복수 사진 허용 여부를 확정해 입력과 저장 계약을 맞춘다. Agent는 `analyze_evidence`를 호출하고 사진 URL 존재 자체가 아니라 구조화된 분석 결과를 판단에 사용한다. 처리 완료, 추가 증빙 요청, Human CS 이관 알림을 제공한다.

#### A-14 · 고객 메시지와 개발용 Trace 분리

고객에게 내부 추론 원문이나 Tool 입력·출력을 노출하지 않는다. 고객 대화에는 고객용 문장만 표시하고, 개발용 화면에서만 `toolHistory`를 확인하게 한다.

#### A-15 · Demo A~E Agent 검증

- Demo A: ETA 전 배달 지연 문의는 정상 진행으로 안내
- Demo B: 저가 누락은 Policy·Risk 안에서 확인 여부와 해결 Action 판단
- Demo C: 필요한 Merchant 확인과 후속 질문 뒤 같은 Case 재개
- Demo D: `CLAIMS_PACKED` 충돌에서 자동 보상 제한 후 해결 불가 시 이관
- Demo E: 오배달 증빙·주문·Merchant Observation으로 허용 Action 판단

예상 결과를 만족하되 Tool 순서와 전용 실행 경로는 고정하지 않는다.

#### A-16 · 기타 문의 진입과 직접 입력

Customer 빠른 선택에 `other`를 추가하고 유형을 고르지 않은 자연어 직접 입력도 허용한다. `other` Case는 공통 계약의 `OUT_OF_SCOPE` Policy 안에서 안내 또는 Human CS 검토를 선택하며, 별도 고정 Workflow를 만들지 않는다.

### 담당자 B

#### B-01 · Human CS 상세에 전체 Risk Flag 표시

`duplicate_refund`, `frequent_refund`, `order_claim_mismatch`, `evidence_mismatch`를 모두 표시한다. 이관 사유, Agent Summary, Policy와 별도 영역으로 구분하고 Flag별 차단 Action을 확인할 수 있게 한다.

#### B-02 · 실제 흐름 연결 후 샘플 기능 제거

A-04, A-08, J-01이 끝나면 Merchant와 Human CS의 샘플 버튼, fixture, locale, 스타일을 제거한다. 주요 제거 대상은 `src/features/merchant/sampleRequest.ts`, `src/features/csDesk/sampleEscalation.ts`와 그 호출부다.

#### B-03 · Demo 초기화 UI 연결 확인

`resetAllDemoCases`가 고객 문장이 든 시작 Case를 새로 만들지 않는지 확인한다. 필요하면 세 화면이 공유하는 Demo 초기화 진입점을 연결한다.

#### B-04 · 샘플 날짜·시각 재현성 수정

현재 `2026-09-30`으로 고정된 주문·배달 시각을 테스트 기준 시각 또는 실행 시점 기준으로 생성하도록 바꾼다. Demo A는 언제 실행해도 ETA 전 정상 진행을 재현하고, A1006·A1007의 지연 판정도 계약의 기대 결과를 유지해야 한다. 시간 계산은 자동 테스트로 고정한다.

### 공동 작업

#### J-01 · 같은 Case의 화면 간 전체 흐름 검증

Customer 접수 → Merchant 확인 → Agent 재개 → 자동 처리 또는 Human CS 이관 → Customer 결과 반영을 한 `caseId`로 확인한다. 중간 단계에서 새 Case를 만들지 않고 구독 중인 화면이 갱신되어야 한다.

#### J-02 · 공통 준비 완료 기준 테스트 추가

`ToolResult`, `history`와 `toolHistory`, 역할별 조회, Merchant `waiting`과 `completed`, Mock Action 저장, Tool 무상태성을 테스트한다. 최대 step, 반복 Tool 실패, Risk 차단, Demo A~E 회귀 테스트도 포함한다.

#### J-03 · 샘플 없는 최종 Demo 검증

고객 문장으로 시작한 Case만으로 Demo A~E를 실행한다. Merchant와 Human CS의 샘플 버튼 없이 실제 Agent가 Queue를 채워야 한다.

#### J-04 · 문서와 현재 코드 동기화

루트 `README.md`, `README/POLICY.md`, 구현 현황의 placeholder·샘플 설명을 실제 상태와 맞춘다. 다른 문서가 ver4.3과 충돌하지 않아야 한다.

#### J-05 · 공통 계약 변경 절차 확인

공통 타입, 상태, Tool 입출력, Policy·Risk 기준, Demo 기대 결과를 바꾸기 전에 A와 B가 합의한다. 계약 변경이 필요한 기능은 계약 문서, 코드, 테스트를 같은 변경에서 갱신한다.

#### J-06 · 가상 로그인과 역할 기반 접근 제어

PoC용 가상 계정을 선택하면 역할과 식별자를 세션에 저장하고 역할별 Route를 보호한다. Customer는 본인 주문·문의만, Merchant는 로그인 계정에 연결된 매장과 확인 요청만, Human CS는 이관 Queue와 처리 이력만 조회한다. 주소를 직접 입력해 다른 역할 화면이나 다른 매장 데이터에 접근할 수 없어야 한다.

## 연결 지점

| 흐름 | A가 저장할 내용 | B가 제공하는 기능 |
| --- | --- | --- |
| 고객 접수 | Case 생성 후 Agent 실행 | Case 생성·저장·구독 |
| Merchant 요청 | 확인 요청 결과, `WAITING_MERCHANT`, 이력·Tool 로그 | 매장별 Queue와 응답·대화 저장 |
| Merchant 확인 | 응답 해석, 후속 질문, `completed`, 본 Loop 재개 | 선택·대화·시각·확인 상태 유지 |
| 자동 처리 | Policy·Risk 범위 안의 Mock Action, 고객 최종 문장 | Mock 환불·재배달 결과 |
| Human CS 이관 | `ESCALATED`, 이관 사유, Agent Summary | Queue, 상세, 최종 처리 저장 |
| 처리 완료 | Customer 결과와 이전 문의에 반영 | Human CS 결과와 `CLOSED` 상태 |

## 완료 판정

다음 조건을 모두 만족하면 화면 간 PoC 연결이 완료된 것으로 본다.

- Customer가 만든 한 Case를 Merchant와 Human CS가 같은 `caseId`로 조회한다.
- Case 변경이 구독 중인 화면에 반영된다.
- `history`와 `toolHistory`가 목적에 맞게 따로 기록된다.
- Merchant 확인이 `waiting`인 동안 최종 Action을 확정하지 않는다.
- Policy와 Risk 결과를 합쳐도 `blockedActions`를 위반하지 않는다.
- Tool이 Case나 다음 행동을 직접 결정하지 않는다.
- Human CS 처리 뒤 Case는 `CLOSED`이고 Agent는 다시 개입하지 않는다.
- Demo A~E가 전용 시나리오 분기 없이 기대 결과를 만족한다.
- 실제 환불·재배달처럼 오해할 표현 없이 Mock 처리임을 표시한다.
- 샘플 버튼 없이 고객 문장으로 시작한 흐름이 끝까지 동작한다.

각 작업의 범위와 완료 기준은 이 문서의 [남은 작업 상세](#남은-작업-상세)를 따른다.
