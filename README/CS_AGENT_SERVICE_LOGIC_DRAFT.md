# 고객 CS Agent 서비스 로직 초안

> 팀 공유 및 정책 합의용 문서
> 작성일: 2026-10-07 KST
> 상태: **논의 초안 — 미확정 정책값은 구현 전에 팀 합의 필요**

## 1. 문서 목적

고객 문의를 단순히 분류해 답변하는 수준을 넘어, AI Agent가 주문·배달·정책·위험 정보를 확인하고 고객, 매장, Human CS를 연결해 실제 해결 단계까지 진행하도록 로직을 정리한다.

이번 범위는 다음 세 문의 유형을 대상으로 한다.

1. 배달이 늦어요
2. 메뉴가 빠졌어요
3. 다른 음식이 왔어요

이 문서는 구현 방향을 맞추기 위한 제안서다. 현재 기준 문서인 `COMMON_AGENT_CONTRACT.md`와 `POLICY.md`를 즉시 대체하지 않는다. 팀 합의가 끝난 항목부터 공통 계약과 Policy에 반영한다.

## 2. 공통 처리 원칙

### 2.1 Agent의 기본 순서

```text
고객 문의 접수
→ 문의 유형과 대상 주문 확인
→ 주문·배달·고객 이력 등 사실 데이터 조회
→ 필요한 증빙과 추가 정보 수집
→ Policy와 Risk 확인
→ 매장 확인이 필요하면 Merchant Agent로 요청
→ 자동 처리 가능 여부 판단
→ 고객 동의를 받은 뒤 환불·재배달·쿠폰 등 Action 실행
→ 자동 처리가 어렵거나 주장이 충돌하면 Human CS 이관
→ 처리 결과와 근거를 고객에게 안내
```

### 2.2 반드시 지킬 원칙

- 고객의 한 문장만으로 환불·재배달을 즉시 확정하지 않는다.
- 환불·재배달·보상 쿠폰 발급 전 고객의 명시적 동의를 받는다.
- 같은 주문과 같은 문제에 동일 Action이 두 번 실행되지 않도록 멱등성을 보장한다.
- LLM은 의도와 대화 맥락을 이해하는 데 사용하되, 금액·횟수·허용 Action은 Policy와 Risk 규칙으로 최종 검증한다.
- 주문에 없는 메뉴를 주장하면 다른 주문을 선택하도록 안내하며, 임의로 환불·재배달하지 않는다.
- 고객 주장과 매장 주장이 충돌하거나 판단 근거가 부족하면 Agent가 사실로 단정하지 않는다.
- 자동 처리할 수 없는 경우에도 지금까지 확인한 정보와 대화 맥락을 Human CS에 함께 전달한다.

## 3. 복합 문의 처리 원칙

복합 문의는 별도의 업무 우선순위를 두지 않고 **고객이 먼저 말한 순서대로 FIFO(선입선출)** 처리한다.

예시:

```text
고객: “배달도 늦었고 콜라도 빠졌어요.”

1번 Task: 배달 지연
2번 Task: 콜라 누락
```

세부 규칙:

- 한 메시지에 여러 문제가 있으면 문장에 등장한 순서대로 Task를 생성한다.
- 여러 메시지로 문제가 추가되면 메시지 전송 시각 순서대로 Queue 뒤에 추가한다.
- 현재 Task가 매장 또는 Human CS 답변을 기다리는 상태가 되면, 대화를 멈추지 않고 다음 Task를 처리한다.
- 외부 답변이 도착하면 대기 중이던 Task를 다시 Queue에 넣어 이어서 처리한다.
- 고객이 “이 문제부터 처리해 주세요”라고 명시하면 고객이 지정한 순서로 변경한다.
- 같은 문제를 반복해서 말하면 새 Task를 만들지 않고 기존 Task의 추가 맥락으로 저장한다.
- 각 Task의 환불·재배달·보상은 서로 별도로 동의를 받는다.
- 모든 Task가 끝나면 문제별 처리 결과를 한 번에 요약한다.
- 식품 안전, 알레르기, 상해 등 긴급 위험 문의는 FIFO의 예외로 즉시 Human CS에 이관한다.

권장 Task 상태:

| 상태 | 의미 |
| --- | --- |
| `QUEUED` | 접수됐으나 아직 처리를 시작하지 않음 |
| `IN_PROGRESS` | Agent가 현재 처리 중 |
| `WAITING_CUSTOMER` | 고객 답변·사진·선택 대기 |
| `WAITING_MERCHANT` | 매장 확인 대기 |
| `WAITING_HUMAN_CS` | Human CS 처리 대기 |
| `RESOLVED` | 처리 완료 |
| `CANCELLED` | 고객 취소 또는 중복 Task 제거 |

## 4. 문의 유형별 로직

## 4.1 배달이 늦어요

### 필요한 데이터

- 선택 주문과 배달 상태
- 예상 도착 시각
- 현재 시각 또는 실제 도착 시각
- 배달원 현재 위치 또는 최근 위치 정보
- 동일 주문의 기존 보상·쿠폰 발급 이력

### 지연 시간 계산

```text
배달 중: 현재 시각 - 예상 도착 시각
배달 완료: 실제 도착 시각 - 예상 도착 시각
```

### 처리 기준

| 실제 지연 | Agent 처리 |
| --- | --- |
| `delayMinutes <= 0` | 정상 진행 안내, 현재 위치 안내, 알림 모드 사용 여부 제안 |
| `1~29분` | 지연 사실과 현재 위치 안내, 알림 모드 제안, 30분 이상 지연 시 보상 기준이 적용됨을 안내 |
| `30분 이상` | 현재 위치와 지연 시간을 안내하고, 중복 보상 여부를 확인한 뒤 보상 쿠폰 발급을 제안 |

### 대화 예시

```text
Agent: 예상 도착 시간보다 현재 18분 늦어지고 있어요.
       현재 배달 위치를 안내해 드릴게요.
       30분 이상 지연되면 보상 기준이 적용되니 안심하고 조금만 기다려 주세요.
       도착 알림을 켜드릴까요?
```

### 추가 규칙

- 고객이 주장한 지연 시간이 아니라 배달 데이터로 계산한 지연 시간을 기준으로 판단한다.
- 고객이 “32분 지연 아닌가요?”라고 물으면 이전 대화와 동일 주문의 배달 데이터를 유지해 바로 설명한다.
- 보상 쿠폰은 모든 지연 고객에게 발급하지 않고 `30분 이상`인 경우에만 제안한다.
- 동일 주문에 이미 지연 보상이 발급됐다면 중복 발급하지 않는다.
- 위치 정보가 없거나 오랫동안 갱신되지 않으면 정확한 위치를 추측하지 않고 Human CS 확인 가능성을 안내한다.

## 4.2 메뉴가 빠졌어요

### 1단계: 주문과 누락 메뉴 확인

Agent는 다음 정보를 확인한다.

- 고객이 선택한 주문
- 누락됐다고 주장한 메뉴명
- 해당 메뉴가 실제 주문에 포함됐는지 여부
- 메뉴 금액과 전체 주문 금액
- 동일 주문의 기존 누락·환불 이력
- 최근 유사 컴플레인 횟수와 Risk Flag

메뉴 표현은 주문 항목과 자연스럽게 매핑한다. 예를 들어 `치킨`은 주문에 있는 `후라이드치킨`을 가리킬 수 있다. 그러나 선택 주문에 없는 `떡볶이`를 임의로 다른 항목에 매핑하면 안 된다.

주문에 없는 메뉴라면:

```text
선택하신 주문에는 떡볶이가 포함되어 있지 않아요.
이 주문의 메뉴는 후라이드치킨과 콜라예요.
다른 주문을 확인해 볼까요?
```

### 2단계: 초기 증빙 수집

- 고객에게 사진 첨부를 요청한다.
- MVP에서는 사진이 없다는 이유만으로 접수를 막지는 않는다.
- 다만 고가 메뉴, 반복 신고, 고객·매장 주장 충돌 시 사진 또는 추가 확인을 필수로 요구할 수 있다.
- 사진은 AI 분석 결과만으로 사실을 확정하지 않고 보조 증빙으로 사용한다.

### 3단계: 고객이 원하는 해결 방식 확인

- 해당 메뉴 부분 환불
- 누락 메뉴 재배달
- 아직 결정하지 못함

고객 선택은 희망 해결 방식일 뿐이며, 이 단계에서 바로 실행하지 않는다.

### 4단계: 모든 누락 문의를 매장에 먼저 확인

누락 메뉴의 가격과 관계없이 Merchant Agent에 다음 내용을 전달한다.

- 주문번호와 메뉴 구성
- 누락 주장 메뉴와 금액
- 고객 설명과 첨부 사진
- 고객이 원하는 해결 방식
- 중복 환불·반복 신고 등 Risk 정보

매장 응답에 따른 처리는 다음과 같다.

| 매장 응답 | Agent의 다음 행동 |
| --- | --- |
| `ADMITTED_MISSING` | 누락 인정. Policy·Risk 재확인 후 고객에게 가능한 환불·재배달 선택지 제안 |
| `POSSIBLE_MISSING` | 누락 가능성은 있으나 해결 미승인. 매장 답변을 고객에게 전달하고 문의 종료 또는 Human CS 연결을 고객이 선택 |
| `CLAIMS_PACKED` | 정상 포장 주장. 매장 답변을 고객에게 전달하고 문의 종료 또는 Human CS 연결을 고객이 선택 |
| `UNKNOWN` | 매장이 판단하기 어려움. 사진 등 추가 자료 요청이 있으면 고객에게 전달하고 같은 Case에서 점주 확인을 재개 |
| 3분간 무응답 | Human CS 이관. 대기 중 다음 고객 Task가 있으면 먼저 처리 |

플랫폼 Human CS는 환불 승인·거절 주체가 아니다. 매장이 문제를 확인하고 해결 조치에 동의하면 고객이 환불 또는 재배달을 선택한다. 매장이 승인하지 않은 경우 고객이 매장 답변을 확인하고 문의를 종료하거나 Human CS의 중재를 직접 요청한다.

### 5단계: 환불 또는 재배달 실행

매장 확인과 Policy·Risk 검토가 끝나면 고객에게 최종 Action을 다시 확인한다.

```text
매장에서 콜라 누락을 확인했어요.
콜라 2,000원을 환불받으시겠어요, 아니면 재배달을 요청하시겠어요?
```

- 환불: 자동 환불 허용 기준을 통과하고 고객이 동의하면 실행
- 재배달: 매장의 재배달 가능 여부, 영업 상태, 거리·배달 가능 시간을 확인한 뒤 실행
- 자동 처리가 막히면 확인한 전체 맥락과 함께 Human CS에 이관

### 자동 환불 기준 제안 — 팀 합의 필요

아래 값은 구현을 위한 **제안값**이며 아직 확정 정책이 아니다.

| 항목 | 제안 기준 |
| --- | --- |
| 누락 메뉴 금액 | 5,000원 이하 |
| 전체 주문 대비 비율 | 전체 주문 금액의 30% 이하 |
| 최근 유사 신고 | 최근 30일 2회 이하 |
| 중복 처리 | 같은 주문·같은 메뉴 환불 이력 없음 |
| Risk | 환불을 차단하는 Risk Flag 없음 |
| 사실 확인 | 매장이 `ADMITTED_MISSING` 또는 `POSSIBLE_MISSING`으로 확인 |
| 고객 동의 | 환불 실행 직전 명시적 동의 |

하나라도 기준을 충족하지 못하면 자동 환불을 실행하지 않고 Human CS 검토 대상으로 전환한다.

## 4.3 다른 음식이 왔어요

### 1단계: 주문과 수령 음식 확인

- 고객이 선택한 주문과 원래 주문 메뉴
- 실제로 받은 음식에 대한 설명
- 포장지, 영수증, 음식 사진
- 주문번호 또는 매장명이 보이는 사진이 있으면 함께 수집

오배달은 누락보다 사진의 판별 가치가 높으므로, 원칙적으로 초기 단계에서 사진을 요청한다.

### 2단계: 매장 확인

모든 오배달 문의는 Merchant Agent에 먼저 확인한다.

| 매장 응답 | Agent의 다음 행동 |
| --- | --- |
| `ADMITTED_MISSING` | 오배달 인정. Policy·Risk 검토 후 재배달 또는 허용된 환불 선택지 제안 |
| `POSSIBLE_MISSING` | 오배달 가능성 있음. 사진과 주문 정보를 함께 검토해 자동 처리 또는 Human CS 결정 |
| `CLAIMS_PACKED` | 정상 포장 주장. 배달 과정에서 주문이 바뀌었을 가능성을 확인하도록 Human CS 이관 |
| `UNKNOWN` | 추가 확인 질문 최대 1회 후 Human CS 이관 |
| 3분간 무응답 | Human CS 이관 |

### 3단계: 해결 방식

- 올바른 메뉴 재배달
- Policy상 허용되는 환불
- 배달원·전달 과정 확인이 필요한 경우 Human CS 이관

오배달 사진과 고객 주장만으로 매장 또는 배달원의 책임을 단정하지 않는다. 매장 확인과 배송 과정 확인 결과를 함께 사용한다.

## 5. Merchant Agent 처리 규칙

### 요청 정보

```text
caseId
orderId
문의 유형
고객 주장
대상 메뉴와 금액
고객 희망 해결 방식
증빙 사진
Policy·Risk 요약
응답 기한
```

### 응답 및 시간 규칙

- 매장에는 구조화된 빠른 응답과 추가 설명 입력을 함께 제공한다.
- `CLAIMS_PACKED`, `UNKNOWN` 응답에는 판단 근거를 한 번 더 요청한다.
- 추가 질문은 최대 1회로 제한해 처리 시간이 무한히 늘어나지 않도록 한다.
- 2분이 지나면 매장 화면에 응답 지연 알림을 표시한다.
- 3분이 지나면 해당 Task를 Human CS에 이관한다.
- 매장 답변이 뒤늦게 도착하더라도 이미 완료된 환불·재배달을 중복 실행하지 않는다.

## 6. Human CS 이관 기준과 전달 정보

### 이관 기준

- 고객과 매장 주장이 충돌함
- 매장 확인이 3분 동안 없음
- 매장이 추가 확인 후에도 `UNKNOWN`
- 자동 환불·재배달 정책 범위를 벗어남
- 주문·배달·증빙 데이터가 부족하거나 서로 불일치함
- Risk가 해당 Action을 차단함
- 식품 안전, 알레르기, 상해 등 긴급 위험 문의

### Human CS 전달 요약

Human CS가 고객에게 같은 내용을 다시 묻지 않도록 다음을 자동 요약해 전달한다.

- 고객과 주문 기본 정보
- 문의 유형과 고객의 원문
- Agent가 확인한 주문·배달 사실
- 고객이 제출한 사진과 분석 결과
- 매장 응답과 추가 설명
- 고객이 원하는 해결 방식
- 적용 Policy와 Risk Flag
- Agent가 이미 수행한 Tool과 결과
- 자동 처리하지 못한 정확한 이유
- Human CS가 결정해야 할 다음 Action

## 7. 고객 대화 UX 원칙

- 고객 화면을 이동하거나 새로고침해도 같은 `caseId`의 대화와 진행 상태를 복원한다.
- 매장 또는 Human CS가 응답하면 기존 고객 채팅에 결과를 이어서 표시한다.
- 현재 상태를 고객용 문구로 보여준다.

| 내부 상태 | 고객 안내 예시 |
| --- | --- |
| `WAITING_CUSTOMER` | “확인을 위해 사진이나 추가 설명을 보내주세요.” |
| `WAITING_MERCHANT` | “매장에 확인 중이에요. 답변을 기다리는 동안 다른 문의도 도와드릴 수 있어요.” |
| `WAITING_HUMAN_CS` | “담당자가 지금까지 확인한 내용을 이어받아 검토 중이에요.” |
| `RESOLVED` | “처리가 완료됐어요. 결과를 확인해 주세요.” |

- “잠시 기다려 주세요”라고만 말한 뒤 아무 변화가 없는 상태를 만들지 않는다.
- 대기 시간이 길어지면 현재 확인 주체와 다음 전환 시점을 안내한다.
- Agent의 내부 추론이나 개발용 Trace는 고객 화면에 노출하지 않는다.

## 8. 현재 구현과 달라지는 핵심 사항

현재 `POLICY.md`에는 저가 누락 메뉴의 경우 매장 확인 전에도 Mock 부분 환불을 허용한다. 이번 논의안은 **가격과 관계없이 모든 누락 및 오배달을 먼저 매장에 확인**하는 방향이다.

따라서 팀 합의 후 다음 변경이 필요하다.

1. `COMMON_AGENT_CONTRACT.md`에서 누락·오배달 확인 절차와 상태 전이를 확정
2. `POLICY.md`의 `LOW_PRICE_MISSING_REFUND` 규칙 수정
3. 매장 확인 전 `mock_refund` 실행을 막는 Guardrail 추가
4. 3분 타임아웃과 Human CS 이관 Trigger 구현
5. 복합 문의 Task Queue와 대기 중 다음 Task 처리 구현
6. 고객 사진 수집과 증빙 분석 결과 연결
7. Merchant 응답 후 고객 선택·동의 단계 연결
8. Human CS 요약 Payload에 전체 대화·Tool·Policy·Risk 포함

## 9. 팀에서 추가로 확정할 사항

아래 항목은 구현 전에 숫자와 범위를 최종 합의해야 한다.

1. 자동 환불 상한: 5,000원을 그대로 사용할지
2. 전체 주문 금액 대비 상한: 30%를 사용할지
3. 반복 신고 기준: 최근 30일 2회 이하를 자동 처리 범위로 볼지
4. `POSSIBLE_MISSING`을 자동 환불 가능한 매장 확인으로 인정할지
5. 누락 사진을 모든 경우 필수로 할지, 분쟁·고가·Risk 상황에서만 필수로 할지
6. 오배달에서 환불을 허용할 조건과 부분·전체 환불 범위
7. 재배달 가능 시간, 영업 종료, 배달 거리 등에 대한 제한 기준
8. 지연 보상 쿠폰의 금액·유효기간·주문당 1회 제한
9. 매장 3분 무응답 기준을 실제 시간으로 적용할지, 데모에서는 단축할지
10. Human CS 이관 후 늦게 도착한 매장 응답을 어떻게 표시할지

## 11. 주요 E2E 검증 시나리오

1. 18분 지연 → 위치·알림 안내, 쿠폰 미발급
2. 32분 지연 → 데이터 기준 32분 설명, 고객 동의 후 쿠폰 1회 발급
3. 콜라 누락 + 매장 인정 → 환불/재배달 선택 → 고객 동의 후 실행
4. 콜라 누락 + 매장 정상 포장 주장 → 자동 환불 금지 → Human CS 이관
5. 콜라 누락 + 매장 3분 무응답 → Human CS 이관
6. 치킨 주문에서 떡볶이 누락 주장 → 주문 불일치 안내 및 다른 주문 선택
7. 오배달 + 사진 + 매장 인정 → 재배달 또는 허용된 환불 선택
8. 배달 지연과 메뉴 누락 동시 문의 → 말한 순서대로 처리, 매장 대기 중 다음 Task 진행
9. 페이지 이동 후 복귀 → 기존 대화와 매장 응답 유지
10. 같은 환불 버튼을 두 번 실행 → 두 번째 Action 차단
